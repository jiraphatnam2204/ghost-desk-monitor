## 2. Built for Year-2 — ออกแบบให้นิสิตปี 2 ทำได้

### กติกาการออกแบบ

| กติกา | แปลว่า |
|---|---|
| **เครื่องมือเดียวกับ lab** | Arduino IDE 2 + esp32 core 3.x · Serial Monitor 115200 baud · ไม่ใช้ ESP-IDF หรือ PlatformIO |
| **ใช้เฉพาะชิ้นที่มี Arduino library และ example ที่คนใช้เยอะ** | ทุกชิ้นเริ่มจากการเปิด *File → Examples* แล้วอัปโหลดให้ทำงานก่อน ค่อยแก้ |
| **ทุกงานยากมีทางถอย** | งานระดับ "ยาก" ทุกตัวมี fallback ที่เขียนไว้ล่วงหน้า และมีเส้นตายตัดสินใจ |
| **ไม่เขียน protocol หรือ parser เอง** | ใช้ ESP-NOW, HTTPS และ library ของ sensor ตามที่มี · ตัด E8 (parser LD2410 เขียนเอง) ออก เพราะหนักเกินไปสำหรับเวลา 6 สัปดาห์ |
| **cloud บริการเดียว** | Supabase: Postgres + REST + Realtime เท่านั้น ไม่ใช้ Edge Functions |
| **ไม่มีแอปและไม่มีล็อกอิน** | ไม่มี LIFF ไม่มีปุ่มเช็กอิน · dashboard เป็นหน้า HTML + JS หน้าเดียว |

## 3. Phase 1 Positioning — ใครคือผู้ใช้ และเราต่างอย่างไร

### Positioning statement (ใช้ในบทนำ proposal และ report)

> สำหรับ **นิสิตที่หาที่นั่งในห้องสมุดช่วงสอบ** ซึ่งเสียเวลาเดินวนหาโต๊ะ แต่เจอแต่โต๊ะที่มีกระเป๋าวางไว้โดยไม่มีคนนั่ง
> **Ghost-Desk Monitor** คือระบบตรวจสถานะรายโต๊ะ ที่แสดงสถานะจริงบนป้ายหมุน 3 หน้าและผังห้องบนเว็บ แล้วเตือนทาง LINE และปล่อยโต๊ะที่ถูกทิ้งไว้โดยอัตโนมัติ — ไม่ต้องจอง ไม่ต้องเช็กอิน
> **ต่างจาก** ระบบจองที่นั่งด้วย QR ทั่วไป ที่รู้แค่ว่า "มีคนจอง" แต่ไม่รู้ว่า "มีคนนั่งอยู่จริงไหม" — เราใช้ mmWave + thermal + กล้อง AI บนบอร์ด และ **ภาพไม่เคยออกจากบอร์ด**

### Proto-personas (สมมติฐาน ยังไม่ได้ยืนยันกับผู้ใช้จริง)

| | ผู้หาที่นั่ง | ผู้ใช้โต๊ะ | เจ้าหน้าที่ห้องสมุด |
|---|---|---|---|
| **บริบท** | มาห้องสมุดช่วงสอบ มีเวลาจำกัด มักมาคนเดียวหรือเป็นกลุ่มเล็ก | นั่งอ่านหลายชั่วโมง ต้องลุกไปกินข้าว เข้าห้องน้ำ | ดูแลหลายห้องพร้อมกัน ไม่ได้อยู่ประจำห้อง |
| **เป้าหมาย** | ได้โต๊ะเร็วที่สุด | ไม่เสียโต๊ะเมื่อลุกไปไม่นาน | ห้องใช้งานได้เต็มที่ ไม่มีของค้าง ไม่แออัด ไม่เสียงดัง |

### Decision Point 1 — มี customer context พอหรือยัง?

**ยังไม่พอ** ทุกอย่างข้างบนมาจากการสังเกตของสมาชิกในทีม ("เห็นบ่อยในห้องสมุด") ยังไม่มีตัวเลขหรือคำพูดของผู้ใช้จริง → ทำ discovery แบบเบาที่สุดที่ทันก่อนส่ง proposal (Phase 2, Decision Point 2) โดยไม่หยุดงานส่วนอื่น เพราะ positioning หลักไม่น่าจะเปลี่ยน แต่ตัวเลขจำเป็นต่อหมวด *Evidence and Detail* (2 คะแนน)

| **ข้อจำกัด** | ห้ามส่งภาพคนออกจากอุปกรณ์ (privacy) · ไม่ต้องเจาะหรือดัดแปลงโต๊ะห้องสมุด · ทีม 5 คน 6 สัปดาห์ · ทำได้ด้วยความรู้ปี 2 |

### Problem statement (ฉบับใช้ใน proposal)

> ช่วงสอบ ห้องสมุดมหาวิทยาลัยมีโต๊ะจำนวนมากที่ถูก "จองด้วยของ" โดยเจ้าของไม่อยู่เป็นเวลานาน ทำให้นิสิตที่ต้องการนั่งจริงหาที่ไม่ได้ ขณะที่เจ้าหน้าที่ไม่มีข้อมูลและไม่มีเวลาเดินตรวจทุกโต๊ะ ระบบจองที่มีอยู่รู้เพียงว่าใครจอง แต่ไม่รู้ว่าคนนั้นยังนั่งอยู่หรือไม่

ช่องตัวเลข (เติมหลัง discovery เท่านั้น): "จากการนับ ______ โต๊ะ ใน 2 รอบห่างกัน 30 นาที พบโต๊ะที่มีของแต่ไม่มีคนต่อเนื่อง > 30 นาที ______% และผู้ตอบแบบสอบถาม ______ คน ______% เคยเจอโต๊ะลักษณะนี้"

### How Might We

> **เราจะทำอย่างไร** ให้โต๊ะในห้องสมุดบอกได้เองว่ามีคนนั่งอยู่จริงหรือไม่ และคืนโต๊ะที่ถูกทิ้งให้คนอื่นได้อย่างยุติธรรม — โดยไม่ต้องให้เจ้าหน้าที่เดินตรวจ ไม่ต้องให้ผู้ใช้เช็กอิน และไม่ต้องส่งภาพคนออกจากโต๊ะ

### Why now

- โจทย์วิชาปีนี้ให้น้ำหนักกับ **คุณภาพงาน embedded** (firmware, การสื่อสารที่เชื่อถือได้, metric จริง) — ปัญหาที่ต้อง "ตรวจสอบการมีอยู่" ต้องใช้ sensor fusion + state machine ที่ gateway ซึ่งตรงกับเกณฑ์พอดี
- sensor ที่จับคนนั่งนิ่งได้ (mmWave 24 GHz) และบอร์ดที่รันโมเดลภาพบนตัวได้ (ESP32-S3 + PSRAM) หาซื้อได้ในไทยในราคานิสิต และมี Arduino library พร้อม example
- Edge Impulse ให้ฝึกโมเดลภาพในเบราว์เซอร์แล้ว export เป็น Arduino library ได้ → AI บนบอร์ดอยู่ในระยะที่นิสิตปี 2 ทำได้
- LINE Notify ปิดบริการแล้ว (มี.ค. 2025) → ใช้ LINE Messaging API แบบ broadcast ซึ่งส่งได้ด้วย HTTPS POST ครั้งเดียวจาก ESP32

### Opportunity Solution Tree

**ตัดออกเพราะ…** แผนเดิมมีการเช็กอินผ่าน QR → LIFF และ LINE push ถึง userId ของคนที่เช็กอิน ตัดออกเพราะต้องทำ webhook, ผูก userId, Edge Function และหน้า LIFF ซึ่งเป็นงานเว็บ backend ที่ไม่ได้ช่วยคะแนนฝั่ง embedded และเกินความรู้ปี 2 ในเวลา 6 สัปดาห์ · แลกกับข้อเสีย: ข้อความ broadcast ถึงทุกคนที่เพิ่มเพื่อน LINE OA ไม่ใช่เฉพาะเจ้าของโต๊ะ จึงต้องระบุชื่อโต๊ะในข้อความ

### Epic hypotheses

| # | Epic | Hypothesis |
|---|---|---|
| EP1 | **Sensor node presence fusion** | เราเชื่อว่า node ที่รวม mmWave + thermal (+ ผล AI) บน FreeRTOS (task + queue แบบ Lab 10) สำหรับ *ผู้ใช้โต๊ะ* จะบอกได้ว่ามีคนนั่งจริงแม้นั่งนิ่ง โดยไม่ถูกหลอกด้วยกระเป๋าหรือแก้วน้ำร้อน · เราจะรู้ว่าถูกเมื่อ false-away (นั่งอยู่แต่ระบบว่าไม่อยู่) ในการทดสอบนั่งนิ่ง 20 รอบ ≤ 1 รอบ (เกณฑ์ที่ตั้งเอง) |
| EP2 | **Prism sign actuator** | เราเชื่อว่าป้ายปริซึม 3 หน้าหมุนด้วย servo 270° สำหรับ *ผู้หาที่นั่ง* จะทำให้รู้สถานะโต๊ะจากทางเดินโดยไม่ต้องเปิดมือถือ · เราจะรู้ว่าถูกเมื่อป้ายหมุนถูกหน้าทุกครั้งใน 20 รอบ และ latency คนลุก → ป้ายหมุน ≤ 3 วิ (ไม่รวม grace 2 นาที) |
| EP3 | **Gateway state machine + ESP-NOW reliability** | เราเชื่อว่า state machine และ timer ทั้งหมดที่ gateway พร้อม ack/retry และ ring buffer ใน RAM สำหรับ *ทุก persona* จะทำให้สถานะถูกต้องแม้ Wi-Fi หรือ cloud ล่ม · เราจะรู้ว่าถูกเมื่อ packet delivery ≥ 99% หลัง retry ในการรัน 24 ชม. และข้อมูลช่วงถอด Wi-Fi ถูกส่งย้อนหลังครบ |
| EP4 | **Cloud + dashboard** | เราเชื่อว่าผังห้อง real-time บนหน้า HTML หน้าเดียว (supabase-js + Realtime บน GitHub Pages) สำหรับ *ผู้หาที่นั่งและ staff* จะใช้ได้โดยไม่ต้องอธิบาย · เราจะรู้ว่าถูกเมื่อเพื่อนที่ไม่เคยเห็นระบบ 4–6 คนหาโต๊ะว่างและเปิดหน้า staff ได้เองโดยไม่ต้องถาม |
| EP5 | **LINE alerts (broadcast)** | เราเชื่อว่า LINE broadcast ที่ระบุชื่อโต๊ะ ส่งจาก gateway ที่นาทีที่ 20 สำหรับ *ผู้ใช้โต๊ะ* จะทำให้ไม่เสียโต๊ะโดยไม่รู้ตัว · เราจะรู้ว่าถูกเมื่อข้อความถึงมือถือที่เพิ่มเพื่อน OA ทุกครั้งในการทดสอบ ภายใน 10 วิหลังครบเวลา และระบุชื่อโต๊ะถูก |
| EP6 | **On-device AI** | เราเชื่อว่าโมเดล Edge Impulse ที่จำแนก `empty` / `person` / `items_only` บน ESP32-S3 สำหรับ *ผู้หาที่นั่งและ staff* จะตัดสินว่าเมื่อคนหายไปแล้วควรปล่อยโต๊ะทันที (โต๊ะโล่ง) นับเวลา (มีแต่ของ) หรือคงสถานะ (ยังมีคนนั่งนิ่ง) — ผล AI เปลี่ยนป้ายโดยตรง จึงปิด loop (M4) · เราจะรู้ว่าถูกเมื่อผ่าน gate 13 พ.ย., precision/recall ≥ 80% ทุก class บน test set ที่แยกไว้ และนับ false release ในการรัน 24 ชม. ได้ |
| EP7 | **Test & metrics harness** | เราเชื่อว่า timestamp ทุกจุด + heartbeat + log ใน Supabase สำหรับ *ทีม (และกรรมการ)* จะทำให้รายงาน metric ได้ครบพร้อม mean/min/max · เราจะรู้ว่าถูกเมื่อดึง metric 4 ตัวออกจาก DB ด้วย SQL ได้โดยไม่ต้องจดมือ |

### Framework ที่ใช้: RICE ฉบับงานที่มีเกณฑ์ให้คะแนน

> **Score = (คะแนน rubric ที่เสี่ยง + คะแนนหักที่เลี่ยงได้) × Confidence ÷ Effort (person-days)**

**ทำไมไม่ใช้ RICE ตรงๆ:** "Reach" ของ RICE คือจำนวนผู้ใช้ แต่ "ตลาด" ของโปรเจกต์นี้คือ rubric 70 คะแนน — สิ่งที่ epic หนึ่งเอื้อมถึงคือคะแนน ไม่ใช่คน และ −2 จาก M1–M8 เป็นต้นทุนที่ต้องนับเท่ากับคะแนนที่ได้ · Confidence สะท้อนความเสี่ยงทางเทคนิค *สำหรับนิสิตปี 2* · Effort นับเป็น person-days ของทีม

## 8. Phase 6 Execution Planning — แตก epic อันดับหนึ่ง และแผน Sprint 1

### แตก EP3 Gateway state machine + ESP-NOW ด้วย splitting patterns

| **Business rule variations** | กติกาแต่ละข้อเป็น story แยก: เห็นคน 60 วิ, ไม่เห็นคน 2 นาทีแล้วถามกล้อง (โล่ง / มีแต่ของ / เห็นคน), เตือน 20 นาที, ปล่อย 30 นาที | US2, US3, US4 |

### User stories

**US1 รับรายงานจาก node** — ในฐานะ gateway ฉันต้องรับ `node_report_t` และรู้ว่ามาจาก node ไหน เพื่อให้ตัดสินสถานะรายโต๊ะได้ · *เริ่มจาก* `ESP_NOW_Broadcast_Slave`
- Given node 1 ส่งรายงานทุก 2 วิ · When gateway ได้รับ · Then Serial Monitor พิมพ์ `rx node=1 seq=…` และอัปเดต last_seen ของ node 1
- Given ได้รับ seq ซ้ำ · When ตรวจ seq · Then ไม่ประมวลผลซ้ำ

**US2 นั่งลง FREE → IN_USE** — ในฐานะผู้หาที่นั่ง ฉันอยากนั่งลงแล้วโต๊ะเป็นของฉันโดยไม่ต้องสแกนอะไร · *เริ่มจาก* sketch state machine ของทีมเอง (switch-case + `millis()`)
- Given โต๊ะ FREE · When node รายงานว่าเห็นคนต่อเนื่อง ≥ 60 วิ · Then สถานะเป็น IN_USE และส่ง SET_SIGN หน้า "ใช้งาน"
- Given โต๊ะ FREE · When มีคนเดินผ่านแล้วหายไปก่อน 60 วิ · Then ยังคง FREE

**US3 ลุกไป: กล้องตัดสิน** — ในฐานะผู้หาที่นั่ง ฉันอยากได้โต๊ะทันทีถ้าเจ้าของกลับไปแล้ว และรู้ว่าโต๊ะไหนเจ้าของแค่ลุกไปชั่วคราว · *เริ่มจาก* state machine เดียวกับ US2 + ค่า `ai_class` ล่าสุดใน `node_report_t`
- Given โต๊ะ IN_USE · When ไม่เห็นคน (mmWave + thermal) ต่อเนื่อง > 2 นาที และ `ai_class` ล่าสุด = `empty` · Then สถานะเป็น FREE ทันที ป้ายหมุนเป็น "ว่าง" และ Serial พิมพ์ `release reason=empty`
- Given เงื่อนไขเดียวกัน · When `ai_class` ล่าสุด = `items_only` · Then สถานะเป็น AWAY ป้ายหมุนเป็น "ไม่อยู่" และเริ่มนับเวลา away
- Given เงื่อนไขเดียวกัน · When `ai_class` ล่าสุด = `person` · Then คง IN_USE (กล้องชนะ mmWave/thermal ที่บอกว่าไม่มีคน) และ Serial พิมพ์ `hold reason=person`
- Given AI ไม่มีผลใหม่เกินเวลาที่ตั้ง (ค่าเริ่มต้นเสนอ 10 วิ ปรับได้) · When ครบ 2 นาที · Then ใช้กติกา 30 นาทีแบบไม่มี AI (เป็น AWAY ทุกกรณี)
- Given AWAY · When เห็นคนอีกครั้ง · Then กลับเป็น IN_USE และรีเซ็ตเวลา away

**US4 เตือนและปล่อยโต๊ะ** — ในฐานะผู้ใช้โต๊ะ ฉันอยากรู้ก่อนจะเสียโต๊ะ และในฐานะผู้หาที่นั่ง ฉันอยากได้โต๊ะที่ถูกทิ้ง · *เริ่มจาก* `BasicHttpsClient` (สำหรับ LINE broadcast)
- Given AWAY · When ครบ 20 นาที · Then gateway ส่ง `POST https://api.line.me/v2/bot/message/broadcast` 1 ครั้ง ข้อความ "โต๊ะ D01 ไม่มีคน 20 นาที จะปล่อยใน 10 นาที" และ Serial พิมพ์ HTTP status 200
- Given AWAY · When ครบ 30 นาที · Then สถานะเป็น FREE ป้ายหมุนเป็น "ว่าง"
- Given ครบ 30 นาที และ `ai_class` ล่าสุดยังเป็น `items_only` · When ปล่อยโต๊ะ · Then ส่ง event `items_left` ขึ้น Supabase ให้ขึ้นหน้า staff
- Given AWAY · When `ai_class` เปลี่ยนเป็น `empty` ก่อนครบ 30 นาที (เจ้าของกลับมาเก็บของแต่ mmWave พลาด) · Then FREE ทันที ไม่ส่ง LINE

**US5 สั่งป้ายแบบมี ack/retry** — ในฐานะทีม ฉันอยากให้คำสั่งหมุนป้ายไม่หายแม้ ESP-NOW ทำ packet ตก · *เริ่มจาก* `ESP_NOW_Broadcast_Master` + send callback
- Given gateway ส่ง SET_SIGN · When send callback รายงานว่าส่งไม่สำเร็จ · Then ส่งซ้ำสูงสุด 3 ครั้ง ด้วย seq เดิม และ Serial พิมพ์ `retry 1/3`
- Given node ได้รับ seq ที่เคยทำแล้ว · When ตรวจ · Then ไม่หมุนซ้ำ

**US6 ส่งขึ้น cloud แบบ store-and-forward** — ในฐานะทีม ฉันอยากให้ข้อมูลไม่หายตอน Wi-Fi หรือ Supabase ล่ม · *เริ่มจาก* `BasicHttpsClient`
- Given สถานะเปลี่ยน · When ส่ง JSON ด้วย HTTPS POST ไป Supabase REST สำเร็จ · Then ได้ status 201 และเอาออกจาก ring buffer
- Given Wi-Fi หลุด · When มีข้อมูลใหม่ · Then เก็บใน ring buffer ใน RAM ตามลำดับเวลา และเมื่อเชื่อมต่อได้ ส่งย้อนหลังครบตามลำดับ (ข้อมูลใน RAM หายถ้าไฟดับ — บันทึกเป็นข้อจำกัดใน report)

**US7 Demo mode** — ในฐานะผู้นำเสนอ ฉันอยากโชว์ flow เตือนและปล่อยโต๊ะได้ใน 10 นาทีของ present · *เริ่มจาก* `BasicHttpsClient` (GET ตาราง settings)
- Given ในหน้า staff กดสวิตช์ demo mode (เขียนลงตาราง `settings`) · When gateway poll ทุก 2 วิ · Then timer เปลี่ยนเป็น 20 วิ / 10 วิ และ dashboard แสดง "DEMO"
- Given ปิด demo mode · When poll ครั้งถัดไป · Then กลับเป็น 20 / 10 นาที

**US8 หลาย node** — ในฐานะกรรมการ ฉันอยากเห็นว่า gateway รองรับหลาย node (scalability 3 คะแนน) · *เริ่มจาก* US1
- Given node จริง 2 ตัว (และ node จำลองถ้ามี) ทำงานพร้อมกัน · When แต่ละตัวเปลี่ยนสถานะ · Then Serial และ dashboard แสดงสถานะแยกตาม node_id ถูกทุกตัว

**US9 node หายไป** — ในฐานะ staff ฉันอยากรู้ว่าโต๊ะไหนอุปกรณ์มีปัญหา ไม่ใช่เข้าใจผิดว่าว่าง · *เริ่มจาก* US1 (last_seen)
- Given node ไม่ส่งรายงานเกินเวลาที่ตั้ง (ค่าเริ่มต้นเสนอ 10 วิ ปรับได้) · When gateway ตรวจ last_seen · Then สถานะเป็น OFFLINE และแสดงบน dashboard โดยไม่เปลี่ยนป้าย

## Appendix A. Architecture — สถาปัตยกรรม

```
[Node D01/D02: FireBeetle 2 ESP32-S3 + cam]   [Gateway: YD-ESP32-23 (ESP32-S3)]        [Cloud]
 LD2410 ─UART + OUT(ISR)─┐                      SCD41 (CO₂) ─I²C─┐
 AMG8833 ─I²C────────────┼─ FreeRTOS tasks      BH1750 ─I²C──────┤                   Supabase
 Camera → Edge Impulse ──┘   (queue/mutex)      MAX4466 ─ADC1────┤   HTTPS POST       ├─ Postgres + REST
 Servo ← SET_SIGN ←─────── ESP-NOW (ack/retry) ─→ State machine   ├─────────────────→  └─ Realtime ─→ Dashboard
                                                RAM ring buffer   │                       (HTML + supabase-js,
                                                LINE broadcast ───┴─ HTTPS POST → LINE      GitHub Pages)
                                                                     Messaging API
 QR บนโต๊ะ → หน้าสถานะโต๊ะ (อ่านอย่างเดียว) + ลิงก์เพิ่มเพื่อน LINE OA
 Dashboard สวิตช์ demo mode → ตาราง settings ← gateway poll ทุก 2 วิ
```

**หลักการแบ่งงาน**
- **Node = รับรู้**: อ่าน sensor, รัน AI, ส่ง "ผล" (ไม่ส่งภาพ), หมุนป้ายตามคำสั่ง
- **Gateway = ตัดสินใจ**: เจ้าของ state machine และ timer ทั้งหมด, ส่งข้อมูลขึ้น Supabase และส่ง LINE เอง → ได้คะแนน "real-time processing on the gateway" ในหมวด II
- **Cloud = จำ + แสดง**: เก็บ raw data และให้ dashboard อ่านแบบ realtime ไม่มีโค้ดฝั่ง server

**Sensor ที่นับใน M1:** node = LD2410, AMG8833 (+ กล้อง) · gateway = SCD41, MAX4466, BH1750 → 5 ชนิดโดยไม่ต้องนับกล้อง

**Cloud: Supabase แบบใช้น้อยที่สุด**
- **Postgres + REST:** gateway ส่ง HTTPS POST ไป `https://<project>.supabase.co/rest/v1/<table>` พร้อม header `apikey` และ `Authorization: Bearer <anon key>` ผ่าน TLS (`WiFiClientSecure`) → E5
- **Realtime:** dashboard subscribe ตารางสถานะด้วย supabase-js
- **ไม่ใช้ Edge Functions** · เปิด RLS: anon insert ได้เฉพาะตารางข้อมูล อ่านได้ทุกตาราง แก้ได้เฉพาะ `settings`
- เป็น SQL → ดึงข้อมูลมาคำนวณ metric ตอนเขียน report ง่าย
- key และ token อยู่ใน `secrets.h` ที่ไม่ commit (มี `secrets.h.example` ให้คนอื่น copy)
- ถ้าทีมอยากได้ MQTT จริงๆ: HiveMQ Cloud (TLS) แต่ต้องมีตัว bridge ไป DB เพิ่ม — ไม่แนะนำเพราะเพิ่มชิ้นที่พังได้

**LINE: gateway ส่ง broadcast เอง**
- LINE Notify ปิดบริการแล้ว (มี.ค. 2025) → ใช้ **LINE Messaging API** ของ Official Account
- `POST https://api.line.me/v2/bot/message/broadcast` header `Authorization: Bearer <channel access token>` body `{"messages":[{"type":"text","text":"โต๊ะ D01 ไม่มีคน 20 นาที จะปล่อยใน 10 นาที"}]}`
- ไม่มี webhook ไม่เก็บ userId · ผู้ใช้เพิ่มเพื่อน OA จากลิงก์ใน QR บนโต๊ะ
- **ตัดออกเพราะ…** LIFF + push ถึง userId ต้องมี webhook และ Edge Function — ไม่จำเป็นต่อ M6

**Dashboard: หน้า HTML + JS หน้าเดียว**
- ใช้ supabase-js ไม่มี framework · host บน GitHub Pages (repo เดียวกับโค้ด)
- **ผังห้อง**: โต๊ะทุกตัวเป็นสีตามสถานะ + เวลาที่เหลือ (realtime) · เปิดจาก QR ด้วย `?desk=D01` เพื่อไฮไลต์โต๊ะนั้น
- **หน้า staff**: โต๊ะที่มีของค้าง, CO₂ (คุณภาพอากาศ + ใช้ประมาณความหนาแน่นคน), ระดับเสียงสัมพัทธ์, สวิตช์ demo mode

## Appendix B. Message format — ร่าง (Architect ต้อง freeze ภายใน 6 พ.ย.)

**Node → Gateway** (ESP-NOW, packed struct, < 250 bytes, ทุก 2 วิ + ทันทีเมื่อสถานะเปลี่ยน)

```c
typedef struct __attribute__((packed)) {
  uint8_t  ver;          // = 1
  uint8_t  node_id;      // 1, 2, ...  ← ได้คะแนน scalability
  uint16_t seq;          // ใช้ ack/retry + นับ packet loss
  uint32_t uptime_ms;
  uint8_t  mmw_state;    // 0 none, 1 moving, 2 still, 3 both (จาก library ld2410)
  uint16_t mmw_dist_cm;
  uint8_t  mmw_energy;
  int16_t  th_max_c10;   // อุณหภูมิสูงสุด ×10
  uint8_t  th_hot_px;    // จำนวน pixel > 30°C
  uint8_t  ai_class;     // 0 empty, 1 person, 2 items_only
  uint8_t  ai_conf;      // 0–100
  uint8_t  sign_face;    // ตำแหน่งป้ายปัจจุบัน
} node_report_t;
```

**Gateway → Node:** `{ver, node_id, seq, cmd=SET_SIGN, face}` · **Ack:** สถานะใน send callback ของ ESP-NOW (ส่งสำเร็จหรือไม่) ถ้าไม่สำเร็จ ส่งซ้ำสูงสุด 3 ครั้ง

**Gateway → Supabase** (HTTPS POST, JSON, ตาราง `desk_events`)

```json
{"node_id":1,"state":"AWAY","away_s":540,"mmw_state":2,"th_max_c10":312,"ai_class":2,"ai_conf":91}
```

**Gateway → Supabase** (ตาราง `room_env` ทุก 1 นาที)

```json
{"co2_ppm":0,"lux":0,"sound_level":0}
```

ค่า 0 ในตัวอย่างเป็นที่ว่าง ไม่ใช่ค่าที่วัดได้ · เวลา (`created_at`) ให้ Postgres ใส่เอง

## Appendix C. State machine — อยู่ที่ gateway

| สถานะ | ป้าย | เข้าเมื่อ | ออกเมื่อ |
|---|---|---|---|
| FREE | ว่าง | เริ่มต้น / คนหายไป 2 นาทีและกล้องเห็นโต๊ะโล่ง / ครบ 30 นาที | เห็นคนต่อเนื่อง ≥ 60 วิ → IN_USE |
| IN_USE | ใช้งาน | เห็นคนต่อเนื่อง ≥ 60 วิ / กลับมานั่ง / คนหายไป 2 นาทีแต่กล้องยังเห็นคน | ไม่เห็นคน > 2 นาที → ดูผล AI ล่าสุด (ตารางถัดไป) |
| AWAY | ไม่อยู่ | คนหายไป 2 นาทีและกล้องเห็นแต่ของ | เห็นคน → IN_USE · กล้องเห็นโต๊ะโล่ง → FREE · ครบ 20 นาที → LINE broadcast · ครบ 30 นาที → FREE + ขึ้นหน้า staff ถ้ายังเป็น `items_only` |
| OFFLINE | ไม่เปลี่ยน | ไม่ได้รับรายงานเกินเวลาที่ตั้ง | ได้รับรายงานอีกครั้ง → สถานะก่อนหน้า |

**เมื่อไม่เห็นคน (mmWave + thermal) ต่อเนื่อง > 2 นาที gateway ดู `ai_class` ล่าสุดของ node นั้น**

| ผล AI ล่าสุด | ตัดสิน | ป้าย | เหตุผล |
|---|---|---|---|
| `empty` (โต๊ะโล่ง) | → **FREE ทันที** (`release reason=empty`) | ว่าง | คนกลับไปแล้วพร้อมของ ไม่ต้องรอ 30 นาที |
| `items_only` | → **AWAY** · 20 นาที LINE เตือน · 30 นาที FREE + ขึ้นหน้า staff ว่ามีของค้าง | ไม่อยู่ | ลุกไปชั่วคราว ให้เวลาเจ้าของกลับ |
| `person` (แต่ mmWave/thermal บอกไม่มีคน) | **คง IN_USE** | ใช้งาน | กล้องชนะ sensor ที่บอกว่าไม่มีคนผิด (เช่น นั่งนิ่งมาก) |
| ไม่มีผลใหม่ (AI ล่ม) | → **AWAY** แล้วใช้กติกา 30 นาทีแบบเดิม | ไม่อยู่ | ระบบยังทำงานได้แม้ไม่มี AI |

ถ้าไม่ผ่าน gate 13 พ.ย. กติกาเดียวกันทุกข้อใช้กับคำตอบจากโน้ตบุ๊ก/Pi

**นี่คือ closed loop ของ M4:** ผล AI ตัดสินโดยตรงว่าจะปล่อยโต๊ะทันที นับเวลา หรือคงสถานะ → gateway ส่ง SET_SIGN → ป้ายหมุน (actuator) · และของค้างขึ้นหน้า staff

**ตัดออกเพราะ…** แบบเดิมเข้า IN_USE ด้วยการเช็กอินผ่าน LIFF + เจอคนภายใน 60 วิ — ตัดเพราะไม่มี LIFF แล้ว การเห็นคนต่อเนื่อง ≥ 60 วิ ทำหน้าที่เดียวกันและไม่ต้องให้ผู้ใช้ทำอะไร

**กรณีขอบที่ต้องตกลงกัน (เรื่องที่ 11):** โต๊ะที่ AI เห็น "มีแต่ของ" แต่ไม่เคยมีคนนั่ง → ป้ายแสดง **ว่าง** (ตามกติกา) และขึ้นหน้า staff หลัง 30 นาที

**AI plan (M4 + E7)**
- **งาน:** จำแนกภาพมองลงโต๊ะเป็น 3 class: `empty` / `person` / `items_only`
- **วิธี:** Edge Impulse ในเว็บเบราว์เซอร์ (ไม่ต้องเขียนโค้ด ML), image classification (MobileNetV2 0.35, 96×96, transfer learning) → export Arduino library แล้วเริ่มจาก example `esp32_camera`
- **ข้อมูล:** ถ่ายจากกล้องบนโต๊ะจริง ~300 ภาพ/class หลายแสง หลายของ (กระเป๋า หนังสือ แก้วน้ำ โน้ตบุ๊ก) เก็บ 20% เป็น test set ห้ามใช้ train
- **Closed loop:** เมื่อคนหายไป 2 นาที `empty` → ปล่อยโต๊ะทันที · `items_only` → AWAY แล้วขึ้นหน้า staff ที่ 30 นาที · `person` → คง IN_USE (กล้องชนะ mmWave/thermal) · node ส่ง `ai_class` และ `ai_conf` ทุกรายงาน gateway ใช้ผลล่าสุด
- **ทำไมไม่ใช้ fusion mmWave+thermal เป็น AI:** ทำได้ แต่เสี่ยงโดนมองว่าเป็น threshold — กล้องตัดสิน "มีแต่ของ" ซึ่ง sensor อื่นทำไม่ได้ จึงเป็นเหตุผลที่ชัดกว่า
- **ถ้าไม่ผ่าน gate:** โน้ตบุ๊กหรือ Pi รันโมเดล Edge Impulse ตัวเดียวกัน รับภาพเฉพาะตอนสถานะเปลี่ยน · E7 → E6
